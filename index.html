    What DevOps means, in one paragraph

    DevOps is the practice of getting code from a developer's laptop into a running, reliable, secure system — quickly and repeatably. Instead of someone clicking around the AWS Console by hand, everything is written down as code, tested automatically, deployed by a pipeline, watched by monitoring, and recoverable when it breaks. A DevOps engineer builds and runs that machinery.

    The guiding principle

    Every month, and every feature inside a month, follows the same loop:

    Learn → Design → Build → Test → Secure → Automate → Document → Demonstrate.

    1. Learn the concept before touching it (short reading, a small experiment).
    2. Design it on paper: what are the parts and how do they talk?
    3. Build the smallest version that works.
    4. Test it, including what happens when it fails.
    5. Secure it: least access, no secrets in code.
    6. Automate anything you would otherwise repeat by hand.
    7. Document it so a stranger could run it.
    8. Demonstrate it with real evidence (screenshots, logs, a short video).

    The goal is not to finish tutorials or collect tool names. The goal is to be able to design, build, test, troubleshoot, explain and demonstrate a working system. A smaller piece of work that is finished and well understood beats a large one that is half-done.

    The 8-step workflow for every feature

    Use this every time you build something, even a small feature. When you work with an AI assistant, ask it to follow these steps too.

    2. Architecture — Which parts are involved and how do they communicate? Sketch it.

    Lesson 0.2b — Bash scripting basics

    Why: DevOps work is full of small jobs you repeat: check your tools, run all the scans, tear down an environment. A bash script turns those commands into one reliable command.

    The pieces you need:

    Piece Example Meaning
    Shebang #!/usr/bin/env bash First line: run this file with bash
    Safety settings set -euo pipefail Stop on the first error, on unset variables, and on failures inside pipes
    Variables name="orders" then echo "$name" No spaces around =; always quote "$name" when using it
    Arguments $1, $2, $@ The first, second, and all arguments given to the script
    Command output today=$(date +%F) Run a command and keep its output
    Arrays and loops tools=(git docker) then for t in "${tools[@]}"; do ...; done Repeat for each item
    Conditions if command -v git > /dev/null; then ...; else ...; fi command -v succeeds if the tool exists; > /dev/null hides its output
    Functions check() { local tool="$1"; ... } Reusable block; local keeps variables inside it
    Exit codes exit 0 / exit 1 0 means success, anything else means failure; pipelines and CI read this

    Your first useful script — create scripts/preflight.sh in your practice folder (you will copy it into the course repository in Month 1):

    #!/usr/bin/env bash
# preflight.sh — check that the tools this course needs are installed, and show their versions.
# Usage: ./scripts/preflight.sh
# Exit code 0 = everything required is present; 1 = something required is missing.

set -euo pipefail
# -e: stop at the first command that fails
# -u: treat an unset variable as an error (catches typos)
# -o pipefail: a pipeline fails if ANY command in it fails, not just the last one

REQUIRED=(git python3 docker aws)
OPTIONAL=(terraform jq)   # installed later in the course
missing=0

check() {
  # $1 = the command name, $2 = "required" or "optional"
  local tool="$1" kind="$2"
  if command -v "$tool" > /dev/null 2>&1; then
    # Print only the first line of the version output.
    printf '  %-10s OK   %s\n' "$tool" "$("$tool" --version 2>&1 | head -n 1)"
  elif [ "$kind" = "required" ]; then
    printf '  %-10s MISSING (required)\n' "$tool"
    missing=$((missing + 1))
  else
    printf '  %-10s not installed yet (optional)\n' "$tool"
  fi
}

echo "Required tools:"
for tool in "${REQUIRED[@]}"; do
  check "$tool" required
done

echo "Optional tools:"
for tool in "${OPTIONAL[@]}"; do
  check "$tool" optional
done

if [ "$missing" -gt 0 ]; then
  echo "Result: $missing required tool(s) missing. Install them, then run this again."
  exit 1
fi
echo "Result: ready."

    Make it executable and run it: chmod +x scripts/preflight.sh && ./scripts/preflight.sh, then echo $? to see its exit code. Real output from a machine without the AWS CLI:

    Lesson 0.3 — Networking you need for DevOps

    • IP address — a machine's address on a network. Port — a numbered door on that machine; a web app might listen on port 8000.
    • DNS — turns a name like example.com into an IP address. You will own a domain from Month 2, so this matters.
    • HTTP/HTTPS — how browsers and apps talk to web servers. HTTPS is HTTP encrypted with TLS, using a certificate that proves the server owns the domain. A request has a method (GET, POST), a path (/health) and gets back a status code (200 OK, 301 redirect, 404 not found, 500 server error, 502/503 usually means the load balancer could not reach a healthy app).
    • localhost / 127.0.0.1 — "this machine". 0.0.0.0 as a listen address means "accept connections from any network interface" — containers need this.
    • In AWS: a VPC is your private network; subnets split it; security groups are per-resource firewalls; a load balancer receives public traffic and forwards it to your app.

    Exercise: Run curl -i https://example.com and identify the status code and two headers in the output.

    Lesson 0.3b — Network troubleshooting toolkit

    Why: "It doesn't connect" has a handful of different causes, and each tool below tells you which one you have. Learning to tell them apart now saves days in Months 1–4.

    Install the tools: sudo apt install -y dnsutils netcat-openbsd iproute2 openssl.

    Question Command What a good answer looks like
    Does the name resolve to an address? dig +short dev.example.com One or more IP addresses. Nothing printed = the DNS name does not exist (yet)
    Is anything listening on this port, on this machine? ss -tlnp A line with your port, e.g. 0.0.0.0:8000. 127.0.0.1:8000 means it only accepts connections from the same machine
    Can I open a connection to that port? nc -zv localhost 8000 Connection to localhost ... succeeded!
    What exactly happens during an HTTP request? curl -v http://localhost:8000/health Lines starting * show connecting; > is what you sent; < is what came back
    Is the HTTPS certificate right? openssl s_client -connect dev.example.com:443 -servername dev.example.com < /dev/null The certificate's subject matches the name you used

    Read the error, then you know where to look. These are the error types you will meet most:

    What you see What it means Where to look next
    curl: (7) Failed to connect ... Couldn't connect to server or nc: ... Connection refused You reached the machine, but nothing is listening on that port Is the app running? Right port? ss -tlnp, docker ps
    curl: (6) Could not resolve host The name has no DNS record (or a typo) dig +short <name>; in AWS, the Route 53 record
    curl: (28) ... timed out Packets get no reply at all: usually a firewall (security group) silently dropping them, or a wrong address Security group rules; is the address right?
    curl: (52) Empty reply from server or (56) ... Connection reset Something accepted the connection but closed it. In containers: the app is listening on 127.0.0.1 instead of 0.0.0.0 The app's --host setting
    HTTP 502 / 503 from a load balancer The load balancer is fine; it has no healthy target to send you to Target group health; the container's logs
    HTTP 404 The server is fine; that path does not exist The URL path

    These are real outputs, from asking for a port with nothing on it and then for one with a server running:

    $ curl -sS http://localhost:8009/health
curl: (7) Failed to connect to localhost port 8009 after 0 ms: Couldn't connect to server
$ nc -zv -w 2 localhost 8009
nc: connect to localhost (127.0.0.1) port 8009 (tcp) failed: Connection refused
$ python3 -m http.server 8010 &        # start a tiny web server in the background
$ nc -zv -w 2 localhost 8010
Connection to localhost (127.0.0.1) 8010 port [tcp/*] succeeded!

    1.1 Concepts in plain English

    • FastAPI — a Python library for building web APIs. You write normal Python functions; FastAPI turns them into HTTP endpoints and validates input using type hints.
    • Container — your app plus everything it needs (Python, libraries, settings) packed into one portable unit. If it runs in a container on your laptop, it runs the same way in AWS. A Dockerfile is the recipe; an image is the built result; a container is a running copy of an image.
    • Amazon ECR (Elastic Container Registry) — a private store for your images, like GitHub but for containers.
    • Amazon ECS (Elastic Container Service) — runs and keeps alive your containers. Key words: a cluster is a group for your services; a task definition is the instruction sheet (which image, how much CPU/memory, which port, which roles); a task is one running copy; a service keeps the desired number of tasks running and replaces failed ones.
    • AWS Fargate — runs ECS tasks without you managing any servers. You pay per second for the CPU and memory you ask for.
    • Application Load Balancer (ALB) — the public front door. It receives HTTP requests and forwards them to healthy tasks in a target group, checking each one with a health check (for example GET /health).
    • IAM roles — identities that AWS services (or GitHub) temporarily assume. Least privilege means each role gets only the permissions it needs.
    • CI/CD — Continuous Integration: every change is automatically built and tested. Continuous Delivery/Deployment: every passing change is automatically released.
    • GitHub Actions — GitHub's built-in automation. A workflow (a YAML file in .github/workflows/) contains jobs, which contain steps.
    • OIDC federation — instead of storing an AWS access key in GitHub, GitHub proves its identity to AWS with a short-lived signed token, and AWS hands back temporary credentials for one specific role. Nothing secret is stored, and the credentials expire in about an hour.
    • CloudWatch Logs — where your container's printed output goes so you can read it later.

    1.2 Architecture

    The request path: a user's browser → ALB (public) → target group → ECS service → Fargate tasks running your container on port 8000 → logs to CloudWatch. The delivery path: you push to GitHub → GitHub Actions runs tests → assumes an AWS role through OIDC → builds and pushes the image to ECR → registers a new task definition → tells the ECS service to deploy it.

    The highlighted OIDC role is the key security idea: GitHub swaps a signed token for temporary AWS credentials, so no access key is ever stored. This month the ALB uses plain HTTP on port 80; Month 2 adds your own domain and HTTPS.

    Cost-saving design choice: run the tasks in public subnets with a public IP and a security group that only accepts traffic from the ALB. This avoids a NAT Gateway (around USD 30+ per month on its own). Private subnets with a NAT Gateway or VPC endpoints are more secure and more typical in companies — write that trade-off in your README.

    1.7 Week 4 — Automate with GitHub Actions and OIDC

    Step 1: let AWS trust GitHub. In IAM → Identity providers, add an OpenID Connect provider with URL https://token.actions.githubusercontent.com and audience sts.amazonaws.com. You create this once per AWS account; every later month reuses it.

    Step 2: create the deploy role github-actions-orders-deploy with this trust policy (infra/iam/github-oidc-trust-policy.json). It says: "only workflows from my aws-devops-platform repository, on the main branch, may assume this role":

    {
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::<ACCOUNT_ID>:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
          "token.actions.githubusercontent.com:sub": "repo:<GITHUB_USER>@<OWNER_ID>/aws-devops-platform@<REPO_ID>:ref:refs/heads/main"
        }
      }
    }
  ]
}

    Why the numbers in the subject? GitHub repositories created after 15 July 2026 send a sub that includes two permanent numeric IDs: repo:OWNER@OWNER_ID/REPO@REPO_ID:.... Your course repository is new, so it uses this format. A policy written the old way (repo:OWNER/REPO:...) is refused with "Not authorized to perform sts:AssumeRoleWithWebIdentity". The IDs are public, not secrets. Get both with:

    curl -s https://api.github.com/repos/<GITHUB_USER>/aws-devops-platform | jq '{repo_id: .id, owner_id: .owner.id}'

    If you reuse a repository created before that date, turn on immutable subject claims in its OIDC settings, so it uses the same format. Only the repo:... start changes; the endings (:ref:..., :environment:..., :pull_request) stay as shown. GitHub's OIDC reference

    The sub condition is the most important security line in this project: without it, any GitHub repository in the world could try to assume your role. Because it names the repository exactly, never rename the repository — if you ever do, update every trust policy at the same time, or the pipeline fails with "Not authorized to perform sts:AssumeRoleWithWebIdentity".

    Step 3: give the role least-privilege permissions (infra/iam/github-deploy-policy.json):

  push:
    branches: [main]

  contents: read
  id-token: write   # allows the job to request the OIDC token

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-python@v7
        with:
          python-version: "3.12"
      - run: pip install -r requirements-dev.txt
      - run: python -m pytest -v

  deploy:
    needs: test          # only runs if tests passed
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7

      - name: Get temporary AWS credentials via OIDC
        uses: aws-actions/configure-aws-credentials@v6
        with:
          role-to-assume: ${{ vars.AWS_ROLE_ARN }}
          aws-region: ${{ vars.AWS_REGION }}

      - name: Log in to ECR
        id: ecr
        uses: aws-actions/amazon-ecr-login@v2

      - name: Build and push image tagged with the commit SHA
        id: build
        env:
          IMAGE: ${{ steps.ecr.outputs.registry }}/orders-api:${{ github.sha }}
        run: |
          docker build -t "$IMAGE" .
          docker push "$IMAGE"
          echo "image=$IMAGE" >> "$GITHUB_OUTPUT"

        id: taskdef
        uses: aws-actions/amazon-ecs-render-task-definition@v1
        with:
          task-definition: infra/ecs/task-definition.json
          container-name: orders-api
          image: ${{ steps.build.outputs.image }}
          environment-variables: |
            APP_VERSION=${{ github.sha }}

      - name: Deploy to ECS and wait until stable
        uses: aws-actions/amazon-ecs-deploy-task-definition@v2
        with:
          task-definition: ${{ steps.taskdef.outputs.task-definition }}
          cluster: orders-cluster
          service: orders-service
          wait-for-service-stability: true

    Read it top to bottom: tests must pass; then GitHub gets a token and swaps it for temporary AWS credentials; the image is tagged with the Git commit SHA so every deployed version is traceable to exact code; the task definition is updated with the new image; ECS rolls out the new version and the job waits until it is healthy.     1.8 Week 5 — Failure testing, rollback and teardown practice

    Failure testing: (1) On a branch, make a test fail and open a PR — confirm CI goes red and nothing deploys. (2) Manually register a task definition that points to an image tag that does not exist (for example orders-api:does-not-exist) and update the service to use it. Watch ECS fail to start the task, read the error in the service's Events tab, then roll back (below). Write down what you saw and how long it took to notice.

    Rollback — every deploy creates a new task definition revision (orders-api:1, :2, :3 ...). To roll back, point the service at the previous good revision:

    aws ecs list-task-definitions --family-prefix orders-api --sort DESC
aws ecs update-service --cluster orders-cluster --service orders-service --task-definition orders-api:<GOOD_REVISION>
aws ecs wait services-stable --cluster orders-cluster --services orders-service
curl http://<ALB-DNS-name>/version

    Alternatively, revert the bad commit in Git and let the pipeline redeploy. Document both, and when you would use each, in docs/runbook.md.

    Teardown (in this order, so nothing is left billing):

    aws ecs update-service --cluster orders-cluster --service orders-service --desired-count 0
aws ecs delete-service --cluster orders-cluster --service orders-service --force
aws elbv2 delete-load-balancer --load-balancer-arn <ALB_ARN>
# wait a minute for the ALB to finish deleting, then:
aws elbv2 delete-target-group --target-group-arn <TG_ARN>
aws ecs delete-cluster --cluster orders-cluster
aws ecr delete-repository --repository-name orders-api --force
aws logs delete-log-group --log-group-name /ecs/orders-api

    Then delete the two security groups in the Console. The IAM roles and OIDC provider cost nothing and stay for Month 2. Finally, check Billing → Bills and the Resource Groups & Tag Editor for anything left behind. Before running any delete command, read it twice and confirm it targets the right resource.

    python scripts/ecs_status.py --cluster orders-dev --region us-east-1

Read-only: it only calls Describe/List APIs.
"""
import argparse
import sys

import boto3


def task_definition_version(ecs, task_definition_arn: str) -> str:
    """Return the APP_VERSION environment value from a task definition, or '?' if absent."""
    task_def = ecs.describe_task_definition(taskDefinition=task_definition_arn)["taskDefinition"]
    for container in task_def["containerDefinitions"]:
        for env in container.get("environment", []):
            if env["name"] == "APP_VERSION":
                return env["value"]
    return "?"


def cluster_report(ecs, cluster: str) -> list[dict]:
    """Collect one row per running task: service, revision, version, image, status, health."""
    rows = []
    service_arns = ecs.list_services(cluster=cluster)["serviceArns"]
    if not service_arns:
        return rows

    services = ecs.describe_services(cluster=cluster, services=service_arns)["services"]
    for service in services:
        task_arns = ecs.list_tasks(cluster=cluster, serviceName=service["serviceName"])["taskArns"]
        tasks = ecs.describe_tasks(cluster=cluster, tasks=task_arns)["tasks"] if task_arns else []
        for task in tasks:
            container = task["containers"][0]
            rows.append({
                "service": service["serviceName"],
                "desired": service["desiredCount"],
                "running": service["runningCount"],
                "revision": task["taskDefinitionArn"].rsplit(":", 1)[-1],
                "version": task_definition_version(ecs, task["taskDefinitionArn"]),
                "image": container.get("image", "?"),
                "status": task.get("lastStatus", "?"),
                "health": task.get("healthStatus", "UNKNOWN"),
            })
    return rows


def main() -> int:
    parser = argparse.ArgumentParser(description=__doc__.splitlines()[0])
    parser.add_argument("--cluster", required=True, help="ECS cluster name, e.g. orders-dev")
    parser.add_argument("--region", default=None, help="AWS Region (default: your configured one)")
    args = parser.parse_args()

    ecs = boto3.client("ecs", region_name=args.region)
    rows = cluster_report(ecs, args.cluster)
    if not rows:
        print(f"No running tasks in cluster {args.cluster}.")
        return 1  # non-zero exit code: useful when a script or pipeline calls this

    print(f"{'SERVICE':<16} {'RUN/WANT':<9} {'REV':<5} {'VERSION':<14} {'STATUS':<9} {'HEALTH':<9} IMAGE")
    for r in rows:
        print(f"{r['service']:<16} {str(r['running']) + '/' + str(r['desired']):<9} {r['revision']:<5} "
              f"{r['version']:<14} {r['status']:<9} {r['health']:<9} {r['image']}")
    return 0


if __name__ == "__main__":
    sys.exit(main())

    2.1 Why Infrastructure as Code?

    In Month 1 you created about ten resources by hand. Could you recreate them exactly, in another Region, in ten minutes? Could a teammate review your change before it happened? Infrastructure as Code (IaC) means describing infrastructure in text files that live in Git. You get history, code review, repeatability and a single command to rebuild or destroy everything.

    2.2 Terraform concepts in plain English

    • Provider — a plugin that knows how to talk to a platform (here, hashicorp/aws).
    • Resource — one thing to create, such as aws_ecr_repository. Written as resource "TYPE" "NAME" { ... }.
    • Variable — an input, so the same code works for dev and staging (var.environment).
    • Output — a value Terraform prints after applying, such as the ALB URL.
    • Data source — reads something that already exists without managing it, such as the list of availability zones (data "aws_availability_zones").
    • Dependencies — Terraform works out the order itself when one resource refers to another (aws_lb.this.arn). depends_on forces an order when it cannot tell.
    • Lifecycle — rules about how a resource is replaced: prevent_destroy (refuse to delete), create_before_destroy, and ignore_changes (do not undo changes made outside Terraform).
    • State — Terraform's record of what it created and the real IDs. It is how Terraform knows what to change. State can contain sensitive values, so it must be protected.
    • Module — a folder of Terraform code you can reuse with different inputs, like a function in Python.
    • Root configuration — a folder you run terraform in (each infra/envs/<env> and infra/global). Each has its own state.
    • The core loop: terraform init (download providers, connect to state) → terraform fmt (tidy formatting) → terraform validate (check syntax) → terraform plan (show what would change) → terraform apply (make the change) → terraform destroy (remove everything).

    Get your domain now (it can take a little while to become active).     Why remote state? By default state is a local file. If your laptop dies, Terraform forgets what it built; if two runs happen at once, state gets corrupted. A dedicated S3 bucket with versioning (to recover old state), encryption, blocked public access and locking solves this.

    Create the bucket once with the CLI (bucket names are global — add your account ID to make it unique):

    BUCKET=tfstate-<ACCOUNT_ID>-us-east-1
aws s3api create-bucket --bucket $BUCKET --region us-east-1
aws s3api put-bucket-versioning --bucket $BUCKET --versioning-configuration Status=Enabled
aws s3api put-public-access-block --bucket $BUCKET \
  --public-access-block-configuration BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true

    Outside us-east-1, create-bucket also needs --create-bucket-configuration LocationConstraint=<REGION>. New S3 buckets are encrypted by default (SSE-S3); confirm it in the bucket's Properties tab. Document these commands in infra/bootstrap/README.md — this is the classic "chicken and egg": the bucket that stores state cannot easily be managed by that same state.

    Automation script: find untagged resources, and test AWS code without AWS

    Tags only help if every resource has them. default_tags handles everything Terraform creates, but anything made by hand, or by a module that overrides tags, can slip through. scripts/check_tags.py finds those, and its exit code makes it usable as a pipeline check:

    #!/usr/bin/env python3
"""Find AWS resources of this project that are missing required tags.

Usage:
    python scripts/check_tags.py
    python scripts/check_tags.py --project orders-platform --region us-east-1

Exit code 0 = every project resource has every required tag; 1 = something is missing.
Note: the Resource Groups Tagging API only lists resources that have (or once had) a tag,
so a resource created with NO tags at all will not appear. Terraform's default_tags prevents that.
"""
import argparse
import sys

import boto3

REQUIRED_TAGS = ["Project", "Environment", "ManagedBy", "Owner"]


def find_missing_tags(tagging, project: str) -> list[tuple[str, list[str]]]:
    """Return (resource ARN, [missing tag keys]) for every project resource missing a tag."""
    problems = []
    paginator = tagging.get_paginator("get_resources")
    # A paginator fetches page after page until AWS says there are no more results.
    for page in paginator.paginate(TagFilters=[{"Key": "Project", "Values": [project]}]):
        for resource in page["ResourceTagMappingList"]:
            present = {tag["Key"] for tag in resource.get("Tags", [])}
            missing = [key for key in REQUIRED_TAGS if key not in present]
            if missing:
                problems.append((resource["ResourceARN"], missing))
    return problems


def main() -> int:
    parser = argparse.ArgumentParser(description=__doc__.splitlines()[0])
    parser.add_argument("--project", default="orders-platform")
    parser.add_argument("--region", default=None)
    args = parser.parse_args()

    tagging = boto3.client("resourcegroupstaggingapi", region_name=args.region)
    problems = find_missing_tags(tagging, args.project)

    if not problems:
        print(f"OK: every resource tagged Project={args.project} has {', '.join(REQUIRED_TAGS)}.")
        return 0

    print(f"{len(problems)} resource(s) missing required tags:")
    for arn, missing in problems:
        print(f"  {arn}\n    missing: {', '.join(missing)}")
    return 1


if __name__ == "__main__":
    sys.exit(main())

    New Python ideas: a paginator keeps asking AWS for the next page of results (AWS returns long lists in pages); {... for ...} builds a set, which makes "is this key present?" quick; a list of tuples (arn, missing) keeps related values together.

    3.1 Concepts in plain English

    • CI vs CD: CI answers "is this change good?" (build + test). CD answers "how do we release it safely?" (deploy, verify, roll back). Keeping them separate means a deploy problem never forces a rebuild, and you deploy exactly what you tested.
    • Build once, promote everywhere: build the image once, then deploy that same image to dev, then staging, then (in theory) prod. Never rebuild for each environment.
    • Semantic versioning: v1.4.2 = MAJOR.MINOR.PATCH. Bump PATCH for fixes, MINOR for new features, MAJOR for breaking changes.
    • Immutable tags: once orders-api:v1.4.2 exists, it can never be overwritten. Turn this on in ECR (image_tag_mutability = "IMMUTABLE" in your Terraform module). Even stronger: deploy by image digest (@sha256:...), the exact fingerprint of the image.
    • Integration test: checks several parts working together (for example the app behind the real load balancer). Smoke test: a few fast checks right after deploying ("is it up, does /version show the new release?").
    • Health checks: the ALB's target-group check decides who gets traffic; an ECS container health check decides whether to restart a task.
    • Rolling deployment: ECS replaces old tasks with new ones a few at a time. Simple, cheap, but old and new versions serve traffic together for a while, and rollback means rolling again.
    • Blue/green deployment: the new version (green) starts alongside the old one (blue). Traffic moves to green — all at once, in a canary step (10% first) or linearly — and if checks fail, traffic goes straight back to blue.
    • Deployment circuit breaker: an ECS setting that notices a rolling deployment whose tasks keep failing and automatically rolls back to the last working version.
    • Approval gate: a pause where a human must approve before the pipeline continues (GitHub environments with required reviewers).

    3.2 Choosing the blue/green mechanism

    There are two AWS-supported ways to do blue/green on ECS. Read the current AWS documentation for both before choosing, and record your decision and reasons in docs/decisions/.

    Option How it works Why choose it
    ECS service with AWS CodeDeploy deployment controller CodeDeploy swaps traffic between two target groups on your ALB, with canary/linear/all-at-once configurations, alarm-based automatic rollback and a test listener Long-established, widely documented, well supported in Terraform (aws_codedeploy_app, aws_codedeploy_deployment_group)
    ECS native blue/green deployment strategy ECS itself manages the two target groups, a bake time and optional lifecycle hooks Fewer moving parts and no separate CodeDeploy resources; newer, so check which Terraform AWS provider version supports it before choosing

    The steps below use CodeDeploy because its concepts are easier to see. Both need: two target groups (blue and green) on the ALB, a production listener (your HTTPS listener on 443), and ideally a test listener (for example HTTPS on port 8443, using the same certificate) where green can be checked before it gets real traffic.

    Environment strategy for this month: dev keeps rolling deployments with the circuit breaker (cheap, fast feedback); staging uses blue/green. This lets you compare both with real measurements.

    3.3 Week 1 — Design the release flow

    The flow you are building in release.yml:

    1. A pull request runs CI (ci.yml: unit tests, image build). Merge to main.
    2. You create a Git tag such as v1.1.0. The build job builds the image once, tags it v1.1.0 and with the commit SHA, pushes it to ECR (immutable), and records the image digest.
    3. The deploy-dev job deploys that digest to dev (rolling) and runs smoke tests against https://dev.<your-domain>.
    4. The deploy-staging job waits for your approval, then starts a blue/green deployment: green starts, health checks run, traffic shifts (canary 10%, then 100%), CloudWatch alarms are watched.
    5. If health checks or alarms fail at any point, traffic returns to blue automatically.
    6. A GitHub Release with notes is created — your release history.

    Define health criteria in writing before building, for example: target group shows all green tasks healthy; /health returns 200; smoke tests pass; the ALB 5XX count stays at zero for 5 minutes. Put these in docs/release-criteria.md.

    Automation script: what version is running where?

    During an incident the first question is "what changed?", and the second is "what is running right now?". scripts/release_info.py answers the second for every environment straight from AWS, including which ECR tags point at the exact image digest:

    #!/usr/bin/env python3
"""Answer "what version is running where?" for every environment, from AWS itself.

Usage:
    python scripts/release_info.py
    python scripts/release_info.py --envs dev staging --region us-east-1

For each environment it reads the ECS service, the task definition it is running,
the image digest, the APP_VERSION, and the ECR tags attached to that exact image.
Read-only. An environment that does not exist (e.g. staging after teardown) is reported, not an error.
"""
import argparse
import sys

import boto3
from botocore.exceptions import ClientError

ECR_REPOSITORY = "orders-api"


def running_release(ecs, ecr, env: str) -> dict:
    """Describe the release currently running in one environment (cluster and service: orders-<env>)."""
    name = f"orders-{env}"
    try:
        services = ecs.describe_services(cluster=name, services=[name])["services"]
    except ClientError as err:  # e.g. ClusterNotFoundException after a teardown
        return {"env": env, "state": f"not found ({err.response['Error']['Code']})"}
    if not services or services[0]["status"] != "ACTIVE":
        return {"env": env, "state": "not found"}

    service = services[0]
    # With CodeDeploy (staging) the running task set is listed under taskSets, not deployments.
    if service.get("taskSets"):
        primary = next((t for t in service["taskSets"] if t["status"] == "PRIMARY"), service["taskSets"][0])
    else:
        primary = next(d for d in service["deployments"] if d["status"] == "PRIMARY")
    task_def = ecs.describe_task_definition(taskDefinition=primary["taskDefinition"])["taskDefinition"]
    container = task_def["containerDefinitions"][0]
    image = container["image"]
    version = next((e["value"] for e in container.get("environment", []) if e["name"] == "APP_VERSION"), "?")

    tags = []
    if "@sha256:" in image:  # deployed by digest (Month 3 onwards): look up which tags point at it
        digest = image.split("@", 1)[1]
        try:
            details = ecr.describe_images(repositoryName=ECR_REPOSITORY, imageIds=[{"imageDigest": digest}])
            tags = details["imageDetails"][0].get("imageTags", [])
        except ClientError:
            tags = ["(image not found in ECR)"]

    return {
        "env": env,
        "state": f"{service['runningCount']}/{service['desiredCount']} running",
        "revision": f"{task_def['family']}:{task_def['revision']}",
        "version": version,
        "tags": ", ".join(tags) or "-",
        "image": image,
    }


def main() -> int:
    parser = argparse.ArgumentParser(description=__doc__.splitlines()[0])
    parser.add_argument("--envs", nargs="+", default=["dev", "staging"])
    parser.add_argument("--region", default=None)
    args = parser.parse_args()

    ecs = boto3.client("ecs", region_name=args.region)
    ecr = boto3.client("ecr", region_name=args.region)
    for env in args.envs:
        info = running_release(ecs, ecr, env)
        print(f"[{info['env']}] {info['state']}")
        if "revision" in info:
            print(f"  task definition : {info['revision']}")
            print(f"  APP_VERSION     : {info['version']}")
            print(f"  ECR tags        : {info['tags']}")
            print(f"  image           : {info['image']}")
    return 0


if __name__ == "__main__":
    sys.exit(main())

    New Python ideas: try / except ClientError catches an AWS error (here, a cluster that does not exist after teardown) and turns it into a readable answer instead of a crash; next((... for ... if ...), default) returns the first matching item, or the default if none match.

    4.1 Concepts in plain English

    • Monitoring vs observability: monitoring tells you that something is wrong (an alarm). Observability lets you work out why by asking new questions of your data.
    • The three signals: logs (detailed records of events), metrics (numbers over time, such as requests per minute), and traces (one request's path through many services — optional here, since you have one service).
    • The "golden signals": latency (how slow), traffic (how much), errors (how many fail), saturation (how full: CPU, memory).
    • Structured logs: logs written as JSON fields ("status": 500, "path": "/orders") instead of free text, so you can filter and count them.
    • SLI (Service-Level Indicator): a measured number that reflects user happiness, for example "percentage of requests that succeed".
    • SLO (Service-Level Objective): your target for that number, for example "99.5% of requests succeed over 30 days".
    • Error budget: the failure you are allowed: 100% minus the SLO. Spend it on releases and experiments; when it runs out, slow down and fix reliability.
    • RTO / RPO: Recovery Time Objective (how long you may be down) and Recovery Point Objective (how much data you may lose).
    • Runbook: step-by-step instructions for a known problem. Postmortem / RCA: a blameless write-up of what happened, why, and what will change.

import logging
import time
import uuid

from fastapi import Request

logging.basicConfig(level=logging.INFO, format="%(message)s")
logger = logging.getLogger("orders-api")


@app.middleware("http")
async def log_requests(request: Request, call_next):
    request_id = request.headers.get("x-request-id", str(uuid.uuid4()))
    start = time.perf_counter()
    response = await call_next(request)
    duration_ms = round((time.perf_counter() - start) * 1000, 1)
    logger.info(json.dumps({
        "level": "INFO",
        "request_id": request_id,
        "method": request.method,
        "path": request.url.path,
        "status": response.status_code,
        "duration_ms": duration_ms,
        "version": APP_VERSION,
    }))
    response.headers["x-request-id"] = request_id
    return response

    What is new here: a middleware runs around every request. async and await let the server handle other requests while waiting — you just need to keep them in this function as written. call_next(request) runs your normal endpoint. async def log_requests(request: Request, call_next):
    """Runs around every request and writes one structured log line for it."""
    request_id = request.headers.get("x-request-id", str(uuid.uuid4()))
    start = time.perf_counter()
    response = await call_next(request)
    duration_ms = round((time.perf_counter() - start) * 1000, 1)

        "request_id": request_id,
        "method": request.method,
        "path": request.url.path,
        "status": response.status_code,
        "duration_ms": duration_ms,
        "version": APP_VERSION,
    }))

    Automation script: how much error budget is left?

    scripts/error_budget.py does the 4.2 calculation with real numbers from CloudWatch, so "are we within our SLO?" becomes a command, not an estimate:

    #!/usr/bin/env python3
"""Calculate the availability SLI and how much error budget is left, from real CloudWatch metrics.

Usage:
    python scripts/error_budget.py --env dev
    python scripts/error_budget.py --env dev --slo 99.5 --days 30

Availability SLI = (requests - 5XX errors) / requests, over the last N days, measured at the
load balancer. Counts both 5XX from the app and 5XX generated by the load balancer itself.
"""
import argparse
import sys
from datetime import datetime, timedelta, timezone

import boto3


def alb_arn_suffix(elbv2, env: str) -> str:
    """CloudWatch identifies a load balancer by the end of its ARN: app/<name>/<id>."""
    arn = elbv2.describe_load_balancers(Names=[f"orders-{env}-alb"])["LoadBalancers"][0]["LoadBalancerArn"]
    return arn.split(":loadbalancer/", 1)[1]


def metric_total(cloudwatch, metric: str, lb_suffix: str, start: datetime, end: datetime) -> float:
    """Sum one Application Load Balancer metric over the whole period."""
    response = cloudwatch.get_metric_data(
        MetricDataQueries=[{
            "Id": "m1",
            "MetricStat": {
                "Metric": {
                    "Namespace": "AWS/ApplicationELB",
                    "MetricName": metric,
                    "Dimensions": [{"Name": "LoadBalancer", "Value": lb_suffix}],
                },
                "Period": 86400,  # one value per day
                "Stat": "Sum",
            },
        }],
        StartTime=start,
        EndTime=end,
    )
    return float(sum(response["MetricDataResults"][0]["Values"]))


def budget(total: float, errors: float, slo_percent: float) -> dict:
    """Pure maths, kept separate so it can be unit-tested without AWS."""
    allowed_errors = total * (1 - slo_percent / 100)
    sli = 100.0 if total == 0 else (total - errors) / total * 100
    used = 0.0 if allowed_errors == 0 else errors / allowed_errors * 100
    return {"sli": sli, "allowed_errors": allowed_errors, "budget_used_percent": used}


def main() -> int:
    parser = argparse.ArgumentParser(description=__doc__.splitlines()[0])
    parser.add_argument("--env", required=True, help="dev or staging")
    parser.add_argument("--slo", type=float, default=99.5, help="availability SLO in percent")
    parser.add_argument("--days", type=int, default=30)
    parser.add_argument("--region", default=None)
    args = parser.parse_args()

    elbv2 = boto3.client("elbv2", region_name=args.region)
    cloudwatch = boto3.client("cloudwatch", region_name=args.region)
    end = datetime.now(timezone.utc)
    start = end - timedelta(days=args.days)

    suffix = alb_arn_suffix(elbv2, args.env)
    total = metric_total(cloudwatch, "RequestCount", suffix, start, end)
    errors = (metric_total(cloudwatch, "HTTPCode_Target_5XX_Count", suffix, start, end)
              + metric_total(cloudwatch, "HTTPCode_ELB_5XX_Count", suffix, start, end))
    result = budget(total, errors, args.slo)

    print(f"Environment      : {args.env} (last {args.days} days)")
    print(f"Requests         : {total:,.0f}")
    print(f"5XX errors       : {errors:,.0f}")
    print(f"Availability SLI : {result['sli']:.3f}%   (SLO {args.slo}%)")
    print(f"Error budget     : {result['allowed_errors']:,.0f} errors allowed, "
          f"{result['budget_used_percent']:.1f}% used")
    if result["budget_used_percent"] >= 100:
        print("Budget exhausted: pause risky releases and fix reliability first.")
        return 1
    return 0


if __name__ == "__main__":
    sys.exit(main())

    5.1 Concepts in plain English

    • DevSecOps: security checks built into every stage of delivery, automatically, instead of a security review at the end. Also called "shifting left".
    • Software supply chain: everything that goes into what you ship — your code, open-source libraries, the base image, GitHub Actions you use, the build system. An attacker can get in through any of them.
    • Vulnerability scanning: comparing your dependencies and image contents against public databases of known flaws (CVEs).
    • SAST (Static Application Security Testing): reading your source code for risky patterns without running it.
    • IaC scanning: checking Terraform for insecure settings, such as a security group open to the world or an unencrypted bucket.
    • Secrets management: keeping passwords and API keys in a managed vault (AWS Secrets Manager) and injecting them at runtime, never in code or images.
    • Pinning: referring to an exact version (fastapi==0.115.0), an exact image digest (python:3.12-slim@sha256:...) or an exact Action commit SHA, so nothing changes under you.
    • SBOM (Software Bill of Materials): an ingredients list of everything inside your image, in a standard format (CycloneDX or SPDX).
    • Provenance / attestation: signed evidence of how and where an artifact was built (which repo, commit and workflow).
    • Image signing: a cryptographic signature proving an image came from you and was not altered (tools: Sigstore cosign, AWS Signer).
    • Threat model: a structured list of what could go wrong, how likely and how bad, and what control addresses it.

    Tool Finds Does not find
    pip-audit Known CVEs in your Python packages and the packages they pull in Flaws in your own code; unknown (zero-day) bugs

# Each step exits non-zero when it finds a problem the gate does not allow — that failure IS the gate.
# Rules and accepted exceptions: docs/security-gates.md
on:

      - name: Code — risky patterns, medium severity and above (Bandit)
        run: bandit -r app scripts -ll

      - name: Infrastructure — insecure Terraform settings (Checkov)

          name: sbom
          path: sbom.cdx.json

Mark the scan job as a required status check on main. release.yml calls this same file (workflow_call), so a release cannot skip the gates (complete file in 5.9).

    Pinning:

    • Python: already pinned with ==. For extra safety, generate hashes (for example with pip-compile --generate-hashes from pip-tools) and install with pip install --require-hashes.
    • Base image: FROM python:3.12-slim@sha256:<digest> (get the digest from docker inspect or Docker Hub). Let Dependabot propose updates.
    • GitHub Actions: pin third-party actions to a full commit SHA, with the version in a comment: uses: owner/action@<40-char-sha> # v4.1.0. Real-world reason: in March 2025 a popular action (tj-actions/changed-files) was compromised and its version tags were moved to malicious code; repos pinned to a SHA were not affected.

    Provenance and signing (concepts plus one practical step): GitHub's actions/attest-build-provenance action can create a signed provenance attestation for your pushed image digest in release.yml (it needs id-token: write and attestations: write permissions; read its README for inputs). Signing tools such as Sigstore cosign or AWS Signer sign the image so a deploy step could refuse unsigned images. Implement provenance if time allows; otherwise document signing as designed but not implemented.

    Audit logging: CloudTrail Event history records management API calls for 90 days at no charge — use it to answer "who changed this security group?". A CloudTrail trail delivering to S3 keeps logs longer (one management-event trail is free; S3 storage is charged). GitHub's repository and organization logs record setting changes. Tools such as GuardDuty and Security Hub add findings but have ongoing costs; enable them only for a short, documented trial.

# Usage: ./scripts/scan-local.sh            (run from the repository root, with your .venv active)

failed=()

run_gate() {
  # $1 = a short name for the gate; the remaining arguments are the command to run.
  local name="$1"
  shift
  echo "===== $name ====="
  if "$@"; then
    echo "PASS: $name"
  else
    echo "FAIL: $name"
    failed+=("$name")
  fi
  echo
}

fi

    Automation script: review IAM roles for over-broad access

    Checkov reviews the IAM you wrote; scripts/iam_wildcards.py reviews what actually exists in the account. That includes anything changed by hand, and the trust policies that decide who can assume each role:

    #!/usr/bin/env python3
"""Review this project's IAM roles for over-broad permissions and loose GitHub trust policies.

Usage:
    python scripts/iam_wildcards.py
    python scripts/iam_wildcards.py --prefixes github- orders-

Severity:
  HIGH   Action "*"; a GitHub (OIDC) trust policy with no "sub" condition or a sub ending in ":*" or matching any repository ("/*")
  MEDIUM a whole service, e.g. "ecs:*"
  LOW    Resource "*" on actions that change things (often unavoidable; check the service docs)
Exit code 1 if anything is HIGH. Read-only.
"""
import argparse
import sys

import boto3

READ_ONLY_PREFIXES = ("Describe", "Get", "List")


def as_list(value) -> list:
    """IAM allows a single string or a list in most fields; treat both the same way."""
    return value if isinstance(value, list) else [value]


def permission_findings(policy_name: str, document: dict) -> list[tuple[str, str]]:
    findings = []
    for statement in as_list(document.get("Statement", [])):
        if statement.get("Effect") != "Allow":
            continue
        actions = as_list(statement.get("Action", []))
        resources = as_list(statement.get("Resource", []))
        for action in actions:
            if action == "*":
                findings.append(("HIGH", f"{policy_name}: allows every action (Action \"*\")"))
            elif action.endswith(":*"):
                findings.append(("MEDIUM", f"{policy_name}: allows the whole service {action}"))
            elif "*" in resources and not action.split(":", 1)[-1].startswith(READ_ONLY_PREFIXES):
                findings.append(("LOW", f"{policy_name}: {action} on Resource \"*\""))
    return findings


def trust_findings(document: dict) -> list[tuple[str, str]]:
    findings = []
    for statement in as_list(document.get("Statement", [])):
        federated = as_list(statement.get("Principal", {}).get("Federated", []))
        if not any("token.actions.githubusercontent.com" in f for f in federated):
            continue
        subs = []
        for operator in statement.get("Condition", {}).values():
            subs += as_list(operator.get("token.actions.githubusercontent.com:sub", []))
        if not subs:
            findings.append(("HIGH", "trust: GitHub OIDC with no 'sub' condition (any repository could assume it)"))
        for sub in subs:
            if sub.endswith(":*"):
                findings.append(("HIGH", f"trust: sub '{sub}' allows any branch, tag or pull request"))
            elif "/*" in sub:
                findings.append(("HIGH", f"trust: sub '{sub}' allows any repository of that owner"))
    return findings


def review_role(iam, role: dict) -> list[tuple[str, str]]:
    name = role["RoleName"]
    findings = trust_findings(role["AssumeRolePolicyDocument"])
    for policy_name in iam.list_role_policies(RoleName=name)["PolicyNames"]:
        document = iam.get_role_policy(RoleName=name, PolicyName=policy_name)["PolicyDocument"]
        findings += permission_findings(f"inline '{policy_name}'", document)
    for attached in iam.list_attached_role_policies(RoleName=name)["AttachedPolicies"]:
        if attached["PolicyArn"].startswith("arn:aws:iam::aws:policy/"):
            continue  # AWS-managed policies are reviewed by AWS; list them in your docs instead
        policy = iam.get_policy(PolicyArn=attached["PolicyArn"])["Policy"]
        version = iam.get_policy_version(PolicyArn=attached["PolicyArn"], VersionId=policy["DefaultVersionId"])
        findings += permission_findings(f"managed '{attached['PolicyName']}'", version["PolicyVersion"]["Document"])
    return findings


def main() -> int:
    parser = argparse.ArgumentParser(description=__doc__.splitlines()[0])
    parser.add_argument("--prefixes", nargs="+", default=["github-", "orders-"])
    args = parser.parse_args()

    iam = boto3.client("iam")
    worst = 0
    order = {"LOW": 1, "MEDIUM": 2, "HIGH": 3}
    for page in iam.get_paginator("list_roles").paginate():
        for role in page["Roles"]:
            if not role["RoleName"].startswith(tuple(args.prefixes)):
                continue
            findings = review_role(iam, role)
            print(f"{role['RoleName']}: {'OK' if not findings else str(len(findings)) + ' finding(s)'}")
            for severity, message in sorted(findings, key=lambda f: -order[f[0]]):
                print(f"  [{severity}] {message}")
                worst = max(worst, order[severity])
    return 1 if worst == 3 else 0


if __name__ == "__main__":
    sys.exit(main())

    #!/usr/bin/env python3
"""Month-to-date cost of this project per environment, plus anything still running after teardown.

Usage:
    python scripts/cost_report.py                 # cost by Environment tag, this month so far
    python scripts/cost_report.py --leftovers     # also list project resources that still exist

Before cost-by-tag works: in Billing > Cost allocation tags, ACTIVATE the "Project" and
"Environment" tags. Costs then appear by tag from that point on (not retroactively), and can
take up to 24 hours to show. Each Cost Explorer API call costs about USD 0.01.
"""
import argparse
import sys
from datetime import date, timedelta

import boto3


def month_to_date(today: date) -> tuple[str, str]:
    """Cost Explorer wants [start, end) dates; on the 1st of the month use yesterday's month."""
    if today.day == 1:
        today = today - timedelta(days=1)
    start = today.replace(day=1)
    end = today + timedelta(days=1)
    return start.isoformat(), end.isoformat()


def cost_by_environment(ce, project: str, start: str, end: str) -> dict[str, float]:
    response = ce.get_cost_and_usage(
        TimePeriod={"Start": start, "End": end},
        Granularity="MONTHLY",
        Metrics=["UnblendedCost"],
        Filter={"Tags": {"Key": "Project", "Values": [project]}},
        GroupBy=[{"Type": "TAG", "Key": "Environment"}],
    )
    totals: dict[str, float] = {}
    for period in response["ResultsByTime"]:
        for group in period["Groups"]:
            env = group["Keys"][0].split("$", 1)[-1] or "(no Environment tag)"  # keys look like "Environment$dev"
            totals[env] = totals.get(env, 0.0) + float(group["Metrics"]["UnblendedCost"]["Amount"])
    return totals


def leftovers(tagging, project: str) -> list[tuple[str, str]]:
    """Every resource still carrying Project=<project>, with its Environment tag."""
    found = []
    for page in tagging.get_paginator("get_resources").paginate(
            TagFilters=[{"Key": "Project", "Values": [project]}]):
        for resource in page["ResourceTagMappingList"]:
            tags = {t["Key"]: t["Value"] for t in resource.get("Tags", [])}
            found.append((tags.get("Environment", "?"), resource["ResourceARN"]))
    return sorted(found)


def main() -> int:
    parser = argparse.ArgumentParser(description=__doc__.splitlines()[0])
    parser.add_argument("--project", default="orders-platform")
    parser.add_argument("--leftovers", action="store_true", help="list project resources that still exist")
    parser.add_argument("--region", default=None, help="Region for the leftovers check")
    args = parser.parse_args()

    start, end = month_to_date(date.today())
    ce = boto3.client("ce", region_name="us-east-1")  # Cost Explorer is a global service served from us-east-1
    totals = cost_by_environment(ce, args.project, start, end)
    print(f"Cost of Project={args.project}, {start} to {end} (USD, unblended):")
    if not totals:
        print("  nothing yet (are the cost allocation tags activated?)")
    for env, amount in sorted(totals.items(), key=lambda kv: -kv[1]):
        print(f"  {env:<22} {amount:>8.2f}")
    print(f"  {'TOTAL':<22} {sum(totals.values()):>8.2f}")

    if args.leftovers:
        tagging = boto3.client("resourcegroupstaggingapi", region_name=args.region)
        found = leftovers(tagging, args.project)
        print(f"\nResources still tagged Project={args.project}: {len(found)}")
        for env, arn in found:
            print(f"  [{env}] {arn}")
        # Global resources (state bucket, ECR repo, roles, zone) are expected to remain until the end.
    return 0


if __name__ == "__main__":
    sys.exit(main())

That let me focus on the pipeline. EC2 gives more control and is cheaper at steady high use, and is needed for special cases (GPUs, host-level agents). For a small service with variable load, Fargate's lower operational work outweighs that.

    2. Walk through what happens from git push to the new version answering. The merge to main triggers deploy.yml. The test job runs pytest; only if it passes does the deploy job start. It requests a GitHub OIDC token, which configure-aws-credentials exchanges for temporary credentials of the deploy role. It logs in to ECR, builds the image, tags it with the commit SHA and pushes it. The render step puts that image and APP_VERSION into the task definition; the deploy step registers a new revision and updates the service. ECS starts a new Fargate task, which pulls the image using the execution role. The task registers in the target group, and the ALB sends it traffic once /health passes. The old task is drained and stopped, and the job waits until the service is stable. Then /version returns the new SHA.

    3. How does GitHub get AWS permissions without an access key? What stops another repository using your role? GitHub signs a short-lived token describing the run: its audience and a subject like repo:<owner>@<owner-id>/aws-devops-platform@<repo-id>:ref:refs/heads/main. AWS STS checks the signature against the OIDC provider registered in my account, then checks the role's trust policy conditions. If they match, it returns credentials that expire in about an hour. Another repository's token has a different sub, so the condition fails and STS refuses. Nothing secret is stored in GitHub at all.

    4. What happens if the container crashes after deployment? The container is essential, so the task stops. The ALB's health checks fail and it stops sending traffic to that target. The ECS service sees running < desired and starts a replacement. With only one task, users get 502/503 errors until the replacement is healthy, which is why production runs at least two tasks across Availability Zones. The task's stopped reason and CloudWatch logs show why it crashed.

    5. Which resources cost money while idle, and roughly how much? The load balancer (about USD 16–20 a month), the Fargate task (about USD 9 a month for 0.25 vCPU and 0.5 GB), and public IPv4 addresses (about USD 3.60 each a month; the ALB and the task each use them). ECR storage and logs cost cents. Roughly USD 30–45 a month in total. I avoided a NAT Gateway (USD 30+ alone) by using public subnets, which is a documented trade-off. I tear down after each session.

    6. How would you roll back a bad release in under five minutes? Every deploy creates a new task definition revision. I list the revisions, point the service at the last good one with aws ecs update-service --task-definition orders-api:<N>, wait for it to be stable, and check /version. That takes a minute or two. Reverting the commit is the alternative, but it waits for the whole pipeline. The key preparation is knowing which revision was good: keep release notes.

    7. What would change if traffic increased tenfold? Raise the desired count to several tasks across AZs, and add ECS service auto scaling (on CPU or requests per target). Maybe increase task size after load testing shows where it breaks. The ALB scales by itself. I would check downstream limits and set alarms before scaling. Costs grow roughly with task count.

    Month 2 — Terraform

    1. What is Terraform state, why is it remote, and what would happen if two people applied at once without locking? State is Terraform's record of which real resources (by ID) belong to which resources in the code. Plans are calculated against it. It is remote (S3) so it is not lost with a laptop, is shared by me and CI, is versioned for recovery, and is encrypted because it can contain sensitive values. Without locking, two applies would read the same state, both make changes, and the last write would overwrite the other's record. State would then disagree with reality, leaving orphaned or duplicated resources.

    2. Why does the ECS service ignore changes to task_definition****? The pipeline owns which image runs: every release registers a new revision. Terraform still remembers its original revision, so without ignore_changes the next apply would roll the service back to an old image. Ownership is split on purpose: Terraform owns the infrastructure, the pipeline owns the release.

    3. What is the difference between plan and apply****, and why save a plan file? plan only calculates and shows what would change; apply makes the changes. Saving the plan (-out) and applying that file guarantees that exactly what was reviewed is applied, even if code or reality changed in between. If state changed meanwhile, the saved plan is refused rather than doing something unexpected.

    4. How do dev and staging stay isolated from each other? They are separate root configurations with separate state files (different keys). Every resource has a distinct name (orders-dev, orders-staging) and its own subdomain. Deploy roles are scoped to each environment's ARNs. A plan in dev cannot touch staging's resources. The honest limit: they share one AWS account; companies usually use separate accounts per environment for a stronger boundary.

    5. Why are the OIDC provider and hosted zone in infra/global****? They exist once per account and are shared by every environment, and they must outlive any environment. If they lived in dev, terraform destroy in dev would delete them and break every pipeline and the domain. Keeping them separate also means only I, from my laptop, can change who is allowed to deploy.

    6. How does ACM know you own the domain? With DNS validation, ACM gives a unique CNAME record name and value. Creating it in the domain's DNS (Terraform does this in Route 53) proves I control the domain; ACM sees it and issues the certificate. The record stays in place, so ACM can renew automatically without any action from me.

    7. Can you recreate the whole platform from an empty account? What must exist first? Yes, by following the order in 2.9. First, the state bucket (bootstrap commands), because Terraform needs somewhere to store state. The domain registration and name servers must be in place outside Terraform. Then apply infra/global, push the bootstrap image, and apply each environment. I proved this with a destroy-and-rebuild.

    8. What would you do if a plan unexpectedly wanted to destroy the load balancer? Not apply. First find out why: a renamed resource, an argument that forces replacement, the wrong folder, or missing variables. Then fix the cause: correct the code, or use a moved block for a rename. If replacement is genuinely needed, I plan it: a new ALB means a new DNS name (the alias record follows) and a short interruption. A surprise destroy in a plan is a stop sign.

    Month 3 — Safe releases

    1. What is the difference between CI and CD in your pipeline, job by job? CI answers "is this change good?": ci.yml on every pull request (tests, image build), and the test job at the start of release.yml. The build job is the hand-over: it creates the one versioned artifact. CD answers "release it safely": deploy-dev (rolling deploy and smoke tests), deploy-staging (approval, then blue/green and smoke tests) and github-release (the record). Keeping them apart means a failed deployment never forces a rebuild.

    2. Why build the image once? What can go wrong if staging rebuilds it? So that what I tested is exactly what I ship. A rebuild can quietly produce a different image: a newer base image layer, a different dependency version, a different build environment. Staging would then run something dev never verified. The digest proves identity: dev and staging run the same sha256.

    3. Why did you delete deploy.yml when adding release.yml****? With both, two pipelines could deploy at the same time and the running version would depend on which finished last. One pipeline means one path to production and a clear release history. The deploy role's trust also moved from the main branch to the dev environment, so the old workflow would no longer be authorized anyway.

    4. What exactly triggers an automatic rollback in your setup? In staging (CodeDeploy): a deployment failure, such as green tasks never becoming healthy or a timeout, or a CloudWatch alarm entering ALARM during the deployment: the 5XX alarm or either unhealthy-hosts alarm. In dev (rolling): the ECS circuit breaker, when new tasks repeatedly fail to start or stay healthy. Important nuance: a failing smoke test fails the pipeline but does not roll back by itself; I would roll back by runbook, or add that as an improvement.

    5. What happens to users during a failed canary? With ECSCanary10Percent5Minutes, 10% of traffic goes to green first. If green fails health checks before taking traffic, users notice nothing. If it fails after the shift, about 10% of requests can fail until the alarm fires (3 bad minutes out of 5), then traffic returns to blue, which is still running. My probe log shows the actual number of failed requests: that is the honest answer, not "zero downtime".

    6. Why are immutable tags or digests important for rollback and auditing? A mutable tag can be moved to a different image, so "roll back to v1.2.0" might deploy something that was never v1.2.0. With immutable tags a version always means the same image, and a digest identifies the exact bytes. For auditing, I can prove which code ran when: the GitHub Release records the digest.

    7. When would you choose rolling instead of blue/green? Rolling when changes are backward compatible, cost and simplicity matter, and a slower rollback is acceptable: dev, internal tools, small teams. Blue/green when you need instant rollback, testing before real traffic, or gradual exposure of a risky change, and can afford briefly running double capacity and more moving parts.

    Month 4 — Observability

    1. Elevated latency is reported. Walk through how you would investigate. (1) Confirm and size it: dashboard p50 and p95, when it started, all paths or one. (2) Correlate with changes: did a release or a config change happen then (release_info.py, GitHub Releases)? Did traffic jump? (3) Check saturation: CPU and memory. (4) Narrow it with logs: the Logs Insights p95-by-time query, then grouped by path, then follow a slow request_id. (5) Mitigate first: roll back or scale out. (6) Confirm recovery on the dashboard, then write the incident up and find the root cause.

    2. What is the difference between an SLI, an SLO and an SLA? An SLI is a measurement (percentage of successful requests). An SLO is my internal target for it (99.5% over 30 days). An SLA is a contractual promise to customers, with consequences such as refunds; it is usually looser than the SLO, so there is a safety margin.

    3. With a 99.9% SLO, how many minutes of full downtime are allowed in 30 days? 30 days is 43,200 minutes; 0.1% of that is 43.2 minutes.

    4. Why use p95 latency instead of the average? The average hides the slow tail. A few very fast requests can make it look fine while 1 in 20 users waits seconds. p95 says "95% of requests are faster than this", which matches what users experience and makes a better alarm.

    5. Why does the 5XX alarm need 3 of 5 datapoints? To ignore single blips (one bad minute from one bad request) that would page someone for nothing. Alert fatigue makes people ignore real alarms. The trade-off is slower detection, about 3 minutes, which my SLO can afford.

    6. What would you add if this became 10 services instead of one? Distributed tracing (for example OpenTelemetry or AWS X-Ray) to follow one request across services; the same log fields and a request ID passed between services; per-service SLOs, dashboards and owners; alert routing to the right team; and a top-level view of the user journeys that matter.

    Month 5 — DevSecOps

    1. Explain your OIDC trust policy line by line. What would happen if the sub condition were removed? Principal: Federated = only tokens issued by GitHub's OIDC provider registered in my account. Action: sts:AssumeRoleWithWebIdentity = the token-exchange call. aud = sts.amazonaws.com = the token was issued for AWS. sub = repo:<owner>@<owner-id>/aws-devops-platform@<repo-id>:environment:staging = only jobs in the staging environment of my repository, which GitHub runs only after my approval. Without sub, any GitHub Actions workflow in any repository in the world could assume the role and do whatever it allows: a complete takeover path.

    2. Where is the payment API key stored, how does it reach the container, and why is its value set outside Terraform? It is in AWS Secrets Manager (orders/<env>/payment-api-key). When a task starts, ECS uses the execution role, which may read only that secret's ARN, to fetch the value and inject it as the PAYMENT_API_KEY environment variable. The value is never in the image, the code, or the task definition. It is set with the CLI because anything Terraform manages ends up in the plan and the state file; Terraform creates only the empty secret.

    3. Your Trivy scan is clean. Is the application secure? No — it means no known vulnerabilities of the kinds Trivy checks in the packages inside the image. It says nothing about my own code's logic or authorization, misconfigured AWS resources, IAM permissions, runtime attacks or unknown (zero-day) flaws. That is why there are several layers: Bandit, Checkov, IAM review, the threat model.

    4. What is an SBOM, and how would you use it when a new critical CVE is announced? A Software Bill of Materials is the ingredients list of an image: every package and version. When a new CVE is announced, I search the stored SBOMs of my releases for the affected package and version. That tells me at once which deployed versions are affected, without rebuilding or rescanning, so I can prioritise patching.

    5. Why pin GitHub Actions to a commit SHA? Version tags like @v4 can be moved to different code by whoever controls the action, including an attacker who compromised it. In March 2025, tj-actions/changed-files had its tags moved to malicious code. A commit SHA cannot be changed, so I run exactly the code I reviewed, and Dependabot proposes updates.

    6. A teammate wants to skip a Checkov check. What process do you require? First, try to fix it. If accepting the risk is right, it must be visible and reviewed: an inline #checkov:skip=ID:reason in the resource, plus an entry in docs/security-gates.md with the reason, the risk accepted, an owner and a review date, approved in a pull request by someone else. No silent, global or permanent skips.

    The end-of-milestone questions (Reference page)

    These nine questions apply to every month; a good answer always names your component, not a general idea.

    Question What a strong answer includes
    Why was this service chosen? The requirement it meets, the alternative you rejected, and the trade-off (cost, effort, control)
    What happens if a component fails? Who detects it (health check, alarm), what recovers it automatically (ECS, CodeDeploy), and what users see meanwhile
    How does authentication work? OIDC with short-lived credentials for pipelines, SSO for you, IAM roles for ECS tasks; no long-lived keys anywhere
    Where are secrets stored? Secrets Manager, read only by the execution role, value set outside Terraform; nothing in Git, images or logs
    What happens when deployment fails? Circuit breaker (dev) or CodeDeploy rollback (staging), what triggers each, and the manual runbook as backup
    How would elevated latency be investigated? The six steps in the Month 4 answer: confirm, correlate, saturation, logs by path, mitigate, confirm recovery
    Can the infrastructure be recreated? Yes, from Terraform plus the bootstrap steps, proven by your clean-room rebuild
    Which resources generate ongoing costs? ALB, Fargate tasks, public IPv4, hosted zone, secrets, alarms and dashboards, with rough monthly figures and your teardown habit
    What would change if traffic increased tenfold? More tasks with auto scaling across AZs, load testing first, alarms in place, and the cost impact

    Interview answers: weak vs strong

    Interviewers are not checking that you know definitions. They are checking that you built something, understood your decisions, and are honest about limits. A strong answer has three parts: what you did, why (including the alternative), and evidence or a limit. Aim for about two minutes, then stop and let them ask more.

    "Why did you use Fargate?"

    • Weak: "Fargate is serverless, so it's better."
    • Strong: "I had one small API with variable load and I wanted to spend my time on delivery, not patching servers. Fargate removes the server management and bills per task-second. I considered EC2: it's cheaper at steady high use and needed for things like GPUs, but neither applied. The trade-off I accepted is less control over the host. If I needed host-level agents, I would revisit it."
    • Why it's stronger: it names the requirement, the alternative and the trade-off, instead of a slogan.

    "How does your pipeline authenticate to AWS?"

    • Weak: "I put the AWS keys in GitHub secrets." (The opposite of what you built, and a red flag.)
    • Strong: "There are no stored keys. GitHub issues a signed OIDC token for each run; AWS checks it against the OIDC provider and the role's trust policy, and returns credentials that expire in about an hour. The trust policy's subject limits each role to one repository and one GitHub environment, so the staging role can only be used after I approve the run. I checked this with a script that flags any trust policy with a wildcard subject."

    "What happens when a release goes wrong?"

    • Weak: "It rolls back automatically."
    • Strong: "It depends on the environment. In staging it's a CodeDeploy blue/green deployment: 10% canary for five minutes, and it rolls back if the new tasks fail health checks or if my 5XX or unhealthy-host alarms fire. I tested this by releasing a version with a deliberate failure switch. My probe log showed [your number] failed requests, so I don't claim zero downtime. In dev, the ECS circuit breaker does the same for rolling deployments. One gap I found: a failed smoke test fails the pipeline but doesn't roll back by itself."
    • Why it's stronger: specifics, a real test, a measured result, and an honest gap. Gaps you found yourself are a strength in an interview.

    "Latency has doubled. What do you do?"

    • Weak: "I'd check the logs."
    • Strong: walk the six steps: confirm on the dashboard (p95 vs p50, which paths, since when), correlate with releases and traffic, check CPU and memory, narrow it down with the Logs Insights p95-by-path query and a slow request ID, mitigate first (roll back or scale out), then find the root cause and write it up. Then add: "I practised this in a drill: I injected 1.5 seconds of latency and the alarm fired after [your number] minutes."

    "What's your SLO, and why that number?"

    • Weak: "99.99%, because high availability is important."
    • Strong: "99.5% availability and 95% of requests under 300 ms, measured over test periods. For a single-task portfolio service, 99.99% would be dishonest: one task restart already risks it. 99.5% gives a budget of about 3.6 hours a month, which is realistic and still useful for deciding when to slow releases down. My error-budget script calculates it from real CloudWatch data."

    "How is HTTPS set up, and what happens when the certificate expires?"

    • Weak: "AWS handles it."
    • Strong: "ACM issues the certificate after DNS validation: Terraform creates the validation record in Route 53. The load balancer terminates TLS on 443 with a TLS 1.3/1.2 policy, and port 80 only redirects. Because the validation record stays in place, ACM renews the certificate automatically before it expires. I'd still alarm on certificate expiry as a safety net."

    "What was your biggest trade-off?"

    • Weak: "I didn't really have to compromise."
    • Strong: "Running tasks in public subnets instead of private subnets behind a NAT Gateway. It saves about USD 30+ a month, which matters for a self-funded project. I limited the risk: the task security group only accepts traffic from the load balancer, and I documented it as a known limitation, along with what I'd change for production."

    "Tell me about something that broke and how you fixed it."

    • Weak: "Nothing major broke." (Nobody believes this, and it wastes your best material.)
    • Strong: use your progress notes. Situation, symptom, how you narrowed it down, the actual cause, the fix, what you changed so it can't recur. For example: "The scheduled drift check failed with 'not authorized'. The cause was that scheduled runs present themselves as the main branch, not as a pull request, and my plan role only trusted pull requests. I added the second subject and documented why."

    "What would change at ten times the traffic?"

    • Weak: "I'd use Kubernetes."
    • Strong: "First I'd load-test to find what breaks first. Likely changes: several tasks across Availability Zones with ECS auto scaling on CPU or requests per target, possibly larger tasks, and private subnets with a NAT Gateway or VPC endpoints once the cost is justified. I'd also add distributed tracing if we split into more services. Kubernetes only if we needed what it offers; ECS handles this scale."

    When you don't know: say so, then reason out loud: "I haven't done that, but here's how I'd approach it...". Never invent production experience, users, uptime or savings. Everything in this course is a portfolio project, and saying that plainly earns trust.
